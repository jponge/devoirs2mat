This is the index plan. It holds no executable steps of its own: each milestone below gets its own plan file, written
just before that milestone starts, approved on its own, and marked `done` when its last step lands. Mark *this* file
`done` only when every milestone is done.

  three tables in **one** `db.select()` via a SQLite JSON-aggregation query, atomic by construction), and
  `src/components/backup-panel.jsx` in the side panel.

  The import path changed shape mid-milestone, for a real reason. The original plan built the whole restore as one
  SQL string (`BEGIN IMMEDIATE … COMMIT;`) sent through the JS plugin's `execute()`. Live-testing against the real
  app (once the screen unlocked — it had been locked for the earlier part of the session, blocking GUI testing
  entirely) found this **actually broken**: a deliberately-failing import (two active courses sharing a name) left
  the pooled connection holding SQLite's write lock, and every write after that failed until the app was restarted.
  Root cause: `tauri-plugin-sql`'s `execute` runs a bare `sqlx::query`, not a `sqlx::Transaction`, so raw
  `BEGIN`/`COMMIT` text gives sqlx no rollback guarantee. Fixed with a new Rust command,
  `import_homework_database` in `src-tauri/src/backup.rs`, which opens a real `sqlx::Transaction` via
  `tauri_plugin_sql::DbInstances` (the plugin's own `pub` app state) — its `Drop` rolls back automatically if
  `commit()` is never reached, a guarantee only available from Rust. `specs/technical-stack.md` is updated in the
  same change; it previously said not to add a Rust command for this, which turned out to be wrong once tested.
  `sqlx` 0.8 (matching `tauri-plugin-sql`'s own resolved version) is now a direct `src-tauri` dependency.

  Review ran in two rounds. Round 1 (JS/TS, before the Rust fix existed) found and fixed one bug: `parseValue` used
  `Number(token)` on a blank value token, and `Number("")` is `0` not `NaN`, so a corrupted file with an empty value
  silently became the number `0` instead of being refused. Round 2 (the Rust fix itself) found nothing must-fix in
  the design, but architecture and quality-engineering independently converged on a real test gap: nothing —
  neither `cargo check` nor the mocked JS suite — would have caught a regression back to the original bug (proven
  by two separate mutations, both passing every existing check). Fixed with three `#[cfg(test)]` tests in
  `backup.rs` against a real in-memory `SqlitePool`, each verified to catch at least one of those two mutations.
  Both the happy path and the failure-and-recovery path were also exercised against the real running app, twice —
  once exposing the bug, once confirming the fix, with `sqlite3` inspecting the actual database file at each step.

  A small unplanned follow-up landed in the same session: homework text now renders bulleted and numbered
  Markdown lists (including nested ones), not just the milestone-8 inline subset — headings, tables, images and raw
  HTML are still excluded. `specs/functional-specs.md` and `specs/technical-stack.md` are updated; Tailwind's
  preflight strips default list markers, so `course-group.jsx` restores them via `components` overrides

## Context

When this roadmap was written on 2026-08-23, `homework/` was still the `create-tauri-app` React starter: a `greet`
command, the three logos, no Tailwind, no database, no i18n, no tests. Milestones 0 and 1 have since changed that;
the milestone table below is the current state. Meanwhile `specs/` fully describes the application we intend to build — a self-contained
desktop homework tracker for a 6–18 year old student, with daily and weekly views, soft-deleted courses, Markdown
homework text, and SQL export/import.

The gap between the two is the whole project. This roadmap breaks it into twelve sequenced milestones, each one a
change that can be reviewed and landed on its own, and each one leaving the application in a runnable state. The
ordering is driven by the dependencies between them: the four items the technical stack lists as "not bootstrapped
yet" come first and each get their own change, as that spec requires; the pure logic that the test suite will pin down
comes before the UI that consumes it; and export/import comes last because it needs the schema to be settled.

Decisions taken with Julien before writing this:

- **Whole application**, organised as milestones.
- **One plan file per milestone**, each with its own `Status:` line, approved and executed independently.
- **Dependencies are approved per milestone**, not in bulk. Each milestone names what it needs and why; stop and ask
  before any install.
- **Renaming is user-visible only**: `productName`, the window title, `<title>`. The `homework/` folder, the cargo
  package `homework` and the identifier `org.ponge.homework` stay as they are — the identifier decides the application
  data directory, and moving it later would orphan an existing `homework.db`.
- Milestone plan files are written **at the start of their milestone**, not all twelve up front: milestone 8's detail
  depends on what the shadcn preset actually generates in milestone 1, and a plan written before that would be fiction
  needing a rewrite.

## Working agreement for every milestone

- Test-driven where there is logic to test. If a behaviour is not pinned down in `specs/`, stop and ask rather than
  inventing it and freezing it in a test.
- Definition of done, per `CLAUDE.md`: `pnpm test` passes, `pnpm tauri dev` starts and the changed screen has actually
  been exercised, `cargo check` passes if Rust was touched, and what was *not* verified is stated plainly.
- A milestone that makes a spec wrong updates that spec in the same change.
- Before asking for review of a completed milestone, launch the `general-purpose` review subagents per `CLAUDE.md` —
  three for anything user-visible or touching persistence, one quality-engineering agent for pure internal helpers —
  briefed to mutation-test and to report must-fix findings only. Report what was fixed and what was deliberately not.
- No commits without explicit approval, and never as co-author.

### Milestone 0 — Name the application Devoirs2mat

Trivial, unblocks nothing, but it is the one thing in the specs that is currently *wrong* rather than merely absent.
`productName`, the window title and the `<title>` that still says "Tauri + React". No dependencies.

### Milestone 1 — Tailwind CSS and the shadcn preset

`pnpm dlx shadcn@latest init` answering **JavaScript** (`components.json` must end with `"tsx": false`), then
`pnpm dlx shadcn@latest apply --preset b7W7uXIq8` — run once and only once, since re-running overwrites the theme.
The `@/` alias, the CSS entry point, and the removal of the starter (`App.css`, the three logos, the `greet` command)
in favour of a minimal shell proving the light and dark palettes. **Record the exact commands and generated files in
`specs/technical-stack.md`**: that spec asks the first person through to do it, and until then nobody can verify the
preset from inside the repository.

Deps to approve: `tailwindcss` and its Vite plugin, plus whatever `shadcn init` pulls in (`class-variance-authority`,
`clsx`, `tailwind-merge`, `lucide-react`, Radix primitives). Risk: the preset id has to still resolve; if it does not,
stop and ask rather than substituting a theme.

### Milestone 2 — Test tooling

`vitest` with `jsdom` and `@testing-library/react`, tests colocated as `src/**/*.test.jsx`, `pnpm test` → `vitest run`
(single shot; watch mode would hang an agent) and `pnpm test:watch`. One meaningful smoke test over the milestone 1
shell, not a placeholder. Update the `CLAUDE.md` sentence that says the test tooling does not exist yet.

Deps to approve: `vitest`, `jsdom`, `@testing-library/react`, and possibly `@testing-library/user-event` and
`@testing-library/jest-dom` — justified individually, not installed reflexively.

### Milestone 3 — Persistence

Comes before i18n because the language preference lives in `settings`.

`tauri-plugin-sql` with the `sqlite` cargo feature, `@tauri-apps/plugin-sql`, and `"sql:default"` in
`src-tauri/capabilities/default.json` — missing any of the three fails at runtime with an opaque permission error.
Migration 1 in `src-tauri/src/migrations.rs` creating `courses`, `homework`, `settings`, the `courses_active_name`
partial unique index and the two `homework` indices, exactly as `specs/data-model.md` specifies; append-only from
there. A thin `src/db/` over a single shared `Database.load("sqlite:homework.db")`, kept thin because it cannot be
tested outside the Tauri runtime. Rust `#[cfg(test)]` tests over the migration list.

**Open question to settle inside this milestone:** the data model requires `PRAGMA foreign_keys = ON` *per
connection*, and the plugin holds a pool, so a one-off pragma from JS would only reach one connection. Check what the
pragma actually reports on a fresh connection and solve it properly if it is off — report the finding either way.

Deps to approve: `tauri-plugin-sql` (cargo, `sqlite` feature), `@tauri-apps/plugin-sql` (pnpm).

### Milestone 4 — Internationalization

`i18next` and `react-i18next`, catalogs in `src/i18n/{en,fr}.json`. Resolution exactly as the functional specs say:
stored `settings.language` wins; absent that, prefix-match the webview locale; anything neither `en` nor `fr` falls
back to English. A hook that persists the choice and applies it immediately with no restart — the visible switch lands
in the drawer in milestone 6, this milestone delivers the mechanism and its tests. `Intl` for dates and numbers; no
date library.

Deps to approve: `i18next`, `react-i18next`.

### Milestone 5 — Calendar and grouping helpers (pure, no UI)

Where the wrong-day bugs live, and the part genuinely worth test-driving. In `src/lib/`, tests first: calendar-date
arithmetic on `YYYY-MM-DD` strings (never `Date` arithmetic, never epoch milliseconds), next/previous day,
next/previous week as exactly ±7 days, the Monday-to-Sunday window containing a date with Monday hard-coded and
never derived from the locale, today as the local system date without a time-zone round-trip, and grouping by course
with `localeCompare`, archived courses last, `created_at, id` inside a group, and `done` in no comparator. Edge cases
the tests must carry: month and year boundaries, 29 February, a due date on a Sunday, and `Éducation physique` before
`Zoologie`.

Deps: none, and explicitly no date library.

### Milestone 6 — Application shell

Top bar with the date selection component, previous/next controls whose step follows the current view, the segmented
Daily / Weekly control that preserves the selected date across a switch, and the drawer button. The drawer itself:
hidden by default, dismissed with `Escape` or a click outside, so the main view always keeps the full window width; it
carries the milestone 4 language switch. A single React context for the shared homework and course data — no state
library, no router. Toast wiring from the preset, ready for the failure paths that follow — and it **must render
the milestone 4 `startupError`**, which `main.jsx` resolves before the first render and `App` currently only logs.
That is the migration-failure toast the functional specs require; it is a prop threaded through the boot path, and a
context refactor is exactly how it would get dropped. It fires twice under `StrictMode` in development, so dedupe it.
Do not put the language in the shared context: `useTranslation` already subscribes consumers to `languageChanged`,
and a second copy would drift from `i18n.language`.

Deps to approve: the shadcn components needed (drawer/sheet, toast, button, and whatever the date control uses),
generated into `src/components/ui/` and never hand-edited.

### Milestone 7 — Courses

Create, rename and delete-as-archive (`courses.archived_at`) from the drawer list. Never `DELETE FROM courses`, and no
second code path for a course no homework has ever used. `localeCompare` ordering with archived after active, from
milestone 5. Pickers offer active courses only, while an entry on an archived course keeps showing its real name,
muted. The first-run empty state: adding homework is disabled until a course exists, with a button opening the drawer
on the course editor.

### Milestone 8 — Displaying homework

**Inherited obligation.** Links are handed to `@tauri-apps/plugin-opener`, which hands them to the operating system.
Take the `href` react-markdown gives the component, never `node.properties.href` from the AST, so the library's own
URL sanitising is not bypassed — and allow-list the scheme (`http`, `https`, `mailto`) before opening. There is no
content-security policy behind this: `"csp"` is deliberately `null`, decided on 2026-08-25, because the Markdown
subset carries no images and no raw HTML for a policy to refuse. This guard is the whole of the defence, and
milestone 10's import is what makes homework text something the student did not necessarily write.

The card, with an always-visible checkbox that writes completion immediately and never reorders or removes anything; a
completed card stays put, checked, muted, struck through. `react-markdown` restricted through `allowedElements` to
bold, italic, inline code, strikethrough and links — no `rehype-raw`, no `dangerouslySetInnerHTML` anywhere, anything
outside the subset shown as the literal characters typed. Links open in the system browser with
`@tauri-apps/plugin-opener` and never navigate the webview. One course-group component used identically by the daily
view and by the weekly view's seven Monday-to-Sunday blocks, laid out on two columns (Friday alone on its row, the
weekend paired) and growing with their content —
the page scrolls, a block never scrolls on its own. Empty areas show a short muted line, never nothing.

Deps to approve: `react-markdown`, plus `remark-gfm` if strikethrough turns out to need it — check rather than assume.

### Milestone 9 — Creating, editing and deleting homework

Quick add: one hover-revealed component shared by the day block and the daily list, inserting a card already in its
edit state; nothing written until `Save`, `Cancel` discards the card, the due date is the day added to and is not
editable while creating. Edit in place: the card becomes the edit state, not a modal, and does not move; text as raw
Markdown in a textarea, plus course and due date; `Save` commits, `Cancel` restores the pre-edit values, `Escape`
equals `Cancel`. Course is the only required field and its error is inline on the field; empty text saves happily.
Delete behind a confirmation dialog — a real `DELETE`, final, no undo. Hover-revealed controls are deliberate:
keyboard and touch parity is out of scope and is not to be "fixed" as an accessibility bug.

### Milestone 10 — Export and import

Last, because it serialises the schema. A restore replaces `settings` too, so `settings.language` can change under
the running application: call `startLanguage()` again after a successful import, and note that importing a database
where the user never chose a language wipes the row and returns the app to detection. Export: a SQL script opening
with `-- devoirs2mat schema-version: N`, `N`
being a code constant bumped alongside any future migration, containing `courses`, `homework` and `settings` only and
never the plugin's `_sqlx_migrations`. Import: a full restore, never a merge — explicit confirmation naming what is
about to be lost, the whole script in one transaction so any failure rolls back, a mismatched header refused outright
rather than partially applied, and the three tables wiped and repopulated but never dropped or created. The parser
must not split on `;`, since homework text may contain one; generator and parser are pure, live in `src/lib/`, and
carry this milestone's heaviest tests, including a round trip and text with semicolons, quotes, newlines and Markdown.
`@tauri-apps/plugin-dialog` picks the path and `@tauri-apps/plugin-fs` reads and writes it, entirely from JavaScript —
both need cargo dependency, JS package **and** capability entries, with an fs scope allowing the path the user picked,
which is the part that is easy to get wrong and fails at runtime rather than at build time.

Deps to approve: `tauri-plugin-dialog` and `tauri-plugin-fs` (cargo), `@tauri-apps/plugin-dialog` and
`@tauri-apps/plugin-fs` (pnpm).

### Milestone 11 — Polish and reconciliation

Subtle appear/disappear animations per the design guidelines, without changing any default component sizes. A pass
over every failure path: nothing silent, unactionable failures toast, in-place-fixable problems inline on the field. A
full review of both catalogues with `Intl` formatting checked in each. A final read of all four specs against the
code, updating anything that drifted.

## Verification, end to end

Per milestone, before asking for review:

1. `pnpm test` from `homework/` — passes and exits.
2. `cargo check`, and `cargo test` where Rust changed, from `homework/src-tauri/`.
3. `pnpm tauri dev`, actually driving the screen the milestone touched. `pnpm dev` is not a substitute: every Tauri
   API call fails there by design.
4. The three review subagents, findings reported split into fixed and deliberately not fixed.
5. A plain statement of what was *not* verified.

The one thing this roadmap cannot verify in advance is milestone 1: nothing in the repository lets anyone confirm what
`shadcn apply --preset b7W7uXIq8` generates until it is run. That is precisely why the technical stack asks the first
person through to write the result down, and why milestone 1 is small and isolated.
