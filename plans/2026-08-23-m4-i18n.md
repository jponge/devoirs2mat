# Milestone 4 — Internationalization

Part of [the roadmap](2026-08-23-roadmap.md). Depends on milestone 3. Every milestone after this one writes
translated strings rather than English literals, which is why it comes before the user interface exists.

## Context

`specs/functional-specs.md` fixes the behaviour precisely:

> On startup the language is the one the user last chose; if there is none yet it is detected from the system locale
> (prefix match on the webview locale), falling back to English for anything that is neither English nor French.
> Changing the language in the side panel persists the choice, takes effect immediately without a restart, and always
> wins over detection afterwards.

`specs/technical-stack.md` fixes the tools — `i18next` and `react-i18next`, catalogs in `src/i18n/{en,fr}.json` — and
`specs/data-model.md` fixes the storage: a `settings` row keyed `language`, absent by default, which is what makes
detection the fallback rather than a stored default.

This milestone delivers the **mechanism**, not the switch. The visible language control lives in the drawer, which is
milestone 6. What lands here is resolution, persistence, the catalogs, and the plumbing that later milestones consume.

It is also **the first code in the application to call `getDatabase()`**, which makes it the milestone that inherits
two things milestone 3 deliberately left open: migrations actually running for the first time, and the startup
failure path that `specs/functional-specs.md` says must reach the user.

## Dependencies requiring approval

| package | why | alternative rejected |
|---|---|---|
| `i18next` | named by the technical stack; the translation core | hand-rolled lookup — cheap at two languages, but the spec names i18next and interpolation/plurals arrive with the real UI |
| `react-i18next` | named by the technical stack; the React bindings and the `useTranslation` hook | reading i18next directly from a context of our own — reimplementing the binding we would be installing anyway |

**Deliberately not requested:** `i18next-browser-languagedetector`. The spec's rule is a prefix match on the webview
locale with an English fallback — four lines of pure JavaScript that we can test exactly, against a dependency whose
default detection order (querystring, cookie, localStorage…) is designed for the web and would need configuring down
to almost nothing. Writing it ourselves is smaller *and* more testable.

## Steps

### 1. Language resolution, as a pure function, tested first

In `src/i18n/`, a function taking the stored value and the webview's list of locales, and returning `en` or `fr`.
This is the whole specified behaviour and it is pure, so it is written test-first:

- a stored `"fr"` wins, whatever the system says
- a stored value that is not `en` or `fr` is ignored, not trusted — the row is user-writable through an import
- no stored value, system `fr-FR` → `fr` (prefix match, not exact)
- no stored value, system `de-DE` → `en` (fallback)
- no stored value, system `["de", "fr-CA", "en"]` → `fr` (first *supported* match wins, not first entry)
- no stored value and no system locale at all → `en`
- case is not significant: `FR-fr` resolves to `fr`

### 2. The catalogs and the i18next setup

`src/i18n/en.json` and `src/i18n/fr.json`, plus the i18next initialisation. English is the fallback language.

Only the strings that exist today: the shell from milestone 1. Do not invent keys for screens that do not exist —
milestones 6 to 11 add their own, and a catalogue full of speculative keys is worse than an empty one.

**A test asserting the two catalogs have identical key sets**, so a French translation can never silently go missing.
That test is the reason this milestone is worth its own change.

### 3. Persistence

Read `settings.language` through the milestone 3 layer; write it when the language changes. A `setLanguage` that
persists, calls `i18n.changeLanguage`, and takes effect with no restart.

Storage is the existing `getSetting`/`setSetting`. Do not add a second persistence path.

### 4. First database call, and the startup failure path

Resolution needs the stored value, so the language is resolved **before the first render** — a single local SQLite
read, which is fast and avoids a visible flash of the wrong language. That means:

- a `catch` around it: if the database cannot be opened or a migration fails, the application still renders, in the
  detected language, and the error is **kept, not swallowed**
- `specs/functional-specs.md` requires a migration error at startup to be reported with a toast. The toast component
  does not exist until milestone 6, so this milestone must hold the error somewhere the milestone 6 toast can read it
  and report it — see the open decision below
- do **not** make the failure silent, and do not let it block the application from starting

### 5. `<html lang>` follows the active language

`index.html` hard-codes `lang="en"`. It must track the active language, for the same reason the theme mirrors the
system appearance. This is the second thing that owns an attribute on `<html>`, after `src/lib/theme.js` — keep them
consistent rather than scattering `documentElement` mutations.

## Not in this milestone

- the visible language switch, which belongs to the drawer in milestone 6
- any `Intl` date or number formatting: the date helpers are milestone 5 and the views that format anything are later
- translating strings for screens that do not exist yet
- a toast component, unless the open decision above goes the other way

## Definition of done

- `pnpm test` and `pnpm build` pass
- the application starts, **creates the database**, and renders in the resolved language
- both languages have been seen working, and the choice survives a restart
- a database failure at startup leaves the application usable and the error retained rather than swallowed
- the two catalogs are proven to have identical keys
- what was not verified is stated plainly

## Outcome (recorded 2026-08-24)

Executed by a subagent, then reviewed by three subagents — the quality and adversarial reviews were killed mid-run by
a session limit and re-run afterwards. The suite went from 107 to 121 tests.

### Delivered

Language resolution as a pure rule with all seven specified cases, `en`/`fr` catalogs with a parity test, persistence
through the milestone 3 settings layer, `<html lang>` following the active language, and the startup error held for
milestone 6. `i18next` 26.4.0 and `react-i18next` 17.0.12 — no language-detector dependency, no toast library.

**The database exists for the first time.** The language read is the first thing to call `getDatabase()`, so
migrations finally ran: `homework.db` under the application config directory, `_sqlx_migrations` showing version 1
succeeded. Both languages were exercised against it and the shell rendered in French.

### Fixed in response to the reviews

- **The startup deadline I added was wrong, and both reviewers caught it.** Racing the database read against a
  timeout stopped a blank window, but it reported "the database did not answer" as an *error* — so a first-run
  migration taking two seconds on a slow disk would have told a child their data was broken, with no way to retract
  it. Worse, the losing read kept going and applied the stored language a moment after paint, reintroducing exactly
  the flash that resolving before render exists to prevent. Now in `src/startup.js`, tested, with a timeout reported
  as a timeout and no error, and a late failure delivered through `onLate`.
- `boot()` extracted to `src/boot.jsx` and tested. The `startupError` prop is the only link carrying a database
  failure to the user, and it lived in `main.jsx`, which nothing may import — so deleting it broke no test. Milestone
  6's context refactor is exactly where that would have evaporated.
- **The catalogue parity test would have rejected a correct translation.** i18next appends CLDR plural categories, and
  they differ per language: English has `one`/`other`, French also has `many`. It now compares base keys, checks each
  language against its own required categories, and catches a key pluralised on one side and flat on the other —
  which the naive version could not express at all.
- `setLanguage` refuses an unsupported language rather than writing it, being normalised away by i18next, and then
  silently ignored on the next launch.
- `lib/document-language.js` is importable without a DOM; it is called at import time, unlike `lib/theme.js`.
- `clearMocks` added after a mock's call history leaked across tests in a file and made one of my own new assertions
  pass for the wrong reason.
- Spec corrections: migrations now run before the first render, and the startup contract is written down.
